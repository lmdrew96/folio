# Codebase Review: Folio
**Date:** 2026-07-10
**Stack:** Next.js 16 (App Router) · Convex · Clerk · TipTap v3 · Tailwind v4 · Anthropic SDK
**Project type:** Personal writing app (single-user, not portfolio-facing) with a read-only MCP door

## Executive Summary

Folio is in excellent shape. The block-as-row data model is a genuinely good architectural bet — it makes per-block attribution, diff-since-last-visit, and the external MCP door all fall out of the schema instead of needing bolt-on parsing logic. Every query/mutation is consistently owner-gated, the PWA setup is complete and already includes a real bug fix (the `clients.claim()` issue), and the code comments throughout explain *why* decisions were made, not just what the code does — genuinely rare and valuable for future-you (or future-Claude) picking this back up. The biggest opportunities are small: document delete has no recovery path, two top-level docs (README, SETUP) have drifted from the current state of the app, and there's no cleanup path for the tombstone/reaction rows that accumulate forever by design.

## High Priority Findings

### 1. Deleting a document is permanent, with no recovery window
- **What:** `documents.remove` (convex/documents.ts:76-104) hard-deletes the document plus all its blocks, visits, and reactions in one mutation. The only safeguard is `DeleteControl`'s two-step inline confirm (click "Delete" once more) — no undo, no trash, no grace period.
- **Why it matters:** This is a writing tool where documents are creative work, not disposable records. A mis-click (or a confirm-click landing before someone reads the label) destroys a document with zero recovery path. The block schema already models soft-delete (`deletedAt` tombstones) for exactly this reason at the block level — the document level never got the same treatment.
- **Suggested action:** Add `deletedAt: v.optional(v.number())` to the `documents` table, make `remove` set it instead of hard-deleting, and filter it out of `documents.list`/`get`. Pair it with a lightweight client-side "Undo" toast (delete now sets the tombstone; a toast offers "Undo" for ~8s before the UI treats it as gone) rather than building a full trash view — that's proportional to a single-user app. A scheduled Convex cron can hard-purge tombstoned documents after some window (30 days) to bound growth.
- **Effort:** Half-day.

## Medium Priority Findings

### 2. No cleanup path for tombstoned blocks or old reactions
- **What:** Soft-deleted blocks (`deletedAt` set) are never purged — they exist only so `diffSince`/`reactionPayload` can report deletions, but nothing ever hard-deletes them once every relevant watermark has passed them. Same for the `reactions` table: every "React to what changed" click persists a row forever; `reactions.recent` just caps the *read* at 20/`limit`, it doesn't cap storage.
- **Why it matters:** Both are unbounded growth by construction. For a document edited heavily over months (TipTap's `UniqueID` mints a fresh id on most splits/pastes), the `blocks` table can accumulate many rows that are pure dead weight, inflating every `by_document` query Folio already runs on every keystroke-adjacent render.
- **Suggested action:** A scheduled Convex cron (e.g. weekly) that hard-deletes blocks tombstoned more than N days ago *and* older than every watermark in `visits` for that document, plus a similar age-based cap on `reactions` (e.g. keep the most recent 50, or 6 months). Not urgent at current scale — worth doing before it's a "why did this doc get slow" mystery.
- **Effort:** Half-day.

### 3. SETUP.md is frozen at "Patch 1," 18+ patches behind reality
- **What:** SETUP.md's own acceptance checklist at the bottom still reads "Patch 1 acceptance check" (boots, Clerk gate, UniqueID, basic save/reload) — it never got updated as multi-doc, attribution, diff, Cleo, MCP, printing, exports, theming, and PWA all shipped (v0.5.0 → v0.18.1 per git log).
- **Why it matters:** This is the file a returning dev — or a fresh Claude session — reads first to understand what's set up and what "done" looks like. Right now it undersells the app by an order of magnitude and could mislead onboarding (e.g. someone assuming attribution/diff aren't wired up yet, when they're core features).
- **Suggested action:** Update the acceptance section (or replace it with a pointer to the git log / a short feature list) to reflect current scope. The setup instructions themselves (Convex/Clerk/Anthropic env steps) are still accurate and don't need to change.
- **Effort:** Quick fix.

### 4. No way to find a document once the desk has more than a screenful
- **What:** `DocList` renders every owned document in a grid, sorted by recency, with no search or filter (convex/documents.ts:5-24, src/components/DocList.tsx:80-134).
- **Why it matters:** Fine today; becomes real friction once there are 20+ documents and the one you want isn't in the first few "recently edited." There's no title search, no sort-by-title option, no tagging/folders.
- **Suggested action:** A simple client-side title filter (input + `.filter()` over the already-fetched `docs` list) would cover this without any schema change, since `documents.list` already returns everything the owner has.
- **Effort:** Quick fix (client-only filter) to Half-day (if paired with a sort-order toggle).

## Low Priority / Nice-to-Have

### 5. README.md is still the unmodified `create-next-app` boilerplate
- **What:** README.md never mentions Folio, its architecture, or SETUP.md — it's the generic scaffold text.
- **Why it matters:** Minor, since SETUP.md carries the real docs, but it's the first file anyone (including GitHub's file browser) shows for the repo.
- **Suggested action:** Replace with a short description + a pointer to SETUP.md.
- **Effort:** Quick fix.

### 6. ResizableDock's max width isn't re-clamped on window resize
- **What:** `maxWidth()` (src/components/ResizableDock.tsx:20-21) is computed once at drag-start / initial state and depends on `window.innerWidth`, but there's no `resize` listener to re-clamp a persisted width if the browser window is later made narrower.
- **Why it matters:** Minor visual edge case — a panel dragged wide on a large monitor could exceed 60% of a subsequently-shrunk window until the user drags the handle again.
- **Suggested action:** Add a `resize` listener that re-clamps `width` against the current `maxWidth()`, or clamp on every render.
- **Effort:** Quick fix.

### 7. `documents.remove` deletes children sequentially, not in parallel
- **What:** convex/documents.ts:84-100 loops `for (const b of blocks) await ctx.db.delete(b._id)` (and the same for visits/reactions) instead of `Promise.all`.
- **Why it matters:** Only matters for documents with very large block counts; at personal-project scale this is unnoticeable.
- **Suggested action:** `await Promise.all(blocks.map((b) => ctx.db.delete(b._id)))` — worth doing at the same time as the soft-delete change in Finding 1, since that code is being touched anyway.
- **Effort:** Quick fix.

## Dimension Summaries

### UI/UX: 🟢 Solid
Calm, consistent, paper-forward visual language; dark mode is a first-class theme (not just inverted colors); mobile gets a proper drawer instead of a squeezed sidebar; loading/empty/error states are handled everywhere they need to be; `aria-live`, `aria-label`, `focus-visible` are used consistently rather than as an afterthought.

### Features: 🟡 Adequate
The full v0/v1 loop (write → attribute → diff → Cleo reacts → export → external siblings read via MCP) is genuinely wired end-to-end, not just backend-with-no-UI or vice versa. Search and document recovery (Findings 1 and 4) are the two visible gaps as the desk grows past a handful of documents.

### MCP: 🟢 Solid
The read-only external door (`folio_list_documents`, `folio_read_document`, `folio_diff_since_last_visit`, `folio_mark_caught_up`) is well-scoped, secret-gated, and internal-query-only so the trust boundary is enforced at the type level, not just by convention. `RESERVED_IDENTITIES` correctly stops an external sibling from reading/advancing Nae's or the in-app Cleo's own watermark. If the read-only-by-design stance ever changes, a scoped `folio_append_block` tool (authored as the sibling's own identity, going through the existing `reconcile` attribution path) would fit the architecture naturally — but that's a deliberate philosophy choice already documented in http.ts, not a gap.

### Architecture: 🟢 Solid
Owner-gating is applied uniformly across every query and mutation with no exceptions found. The fractional-index reordering (`computeOrders`) and hash-based skip-if-unchanged sync are both non-obvious and both correctly commented with their known limits (float drift is already flagged as accepted v1 debt in the code itself). The one thing worth tracking going forward is unbounded tombstone/reaction growth (Finding 2).

### Infrastructure: 🟢 Solid
PWA is fully wired (manifest, generated icons at three sizes, service worker, offline fallback page, install prompt) and the service worker's deliberate avoidance of `clients.claim()` is a real bug fix, not a hypothetical concern. No CI pipeline exists, but that lines up with the established solo build-verify-then-ship workflow rather than reading as an oversight.

### DX: 🟡 Adequate
Inline code comments are the standout strength of this codebase — they consistently explain the *why* behind non-obvious choices (order computation, debounce/hash skip, SW claim avoidance, `@page` needing to stay unnested). The gap is one level up: the two docs meant to orient a human (README, SETUP) haven't kept pace with the code (Findings 3 and 5).

## Strengths

- **Block-as-row is doing real work.** Per-block attribution, diff-since-last-visit, and the external MCP read door all fall out of one schema decision instead of three separate subsystems.
- **Consistent auth discipline.** Every Convex function checks `ctx.auth.getUserIdentity()` and compares `ownerId` before touching data — no shortcuts found anywhere, including the MCP path, which uses a completely separate internal-only query layer so the public editor path can never regress from the external-facing one.
- **Documented tradeoffs age well.** Several non-obvious decisions (float-drift ordering, no `clients.claim()`, `@page` staying unnested past a Turbopack CSS bug) are explained in place, so a future reader won't "fix" them into a regression.
- **Export pipeline is thorough without bloating the bundle.** Six formats (PDF via print, DOCX, MD, RTF, HTML, TXT) share one JSON walk, and `docx` is dynamically imported so it never enters the main client bundle.
- **The continuity design (Cleo) is unusually deliberate.** Live-fetching pctx/Tangle edges per-request (with soft-fail fallback to baked identity) rather than baking a static system prompt is a thoughtful choice that keeps the in-app sibling consistent with the rest of the Claude family instead of drifting into its own snapshot.
